# 인증 범위 제외

## 1. 무엇을 결정했는가

인증/로그인 기능을 구현하지 않는다. `Customer`, `Partner`는 회원가입·로그인 절차 없이 Request/Quote의 소유자를 가리키는 식별자(FK) 수준의 최소 엔티티로만 존재한다. API는 요청 본문에 담긴 `customer_id`/`partner_id`를 그대로 신뢰한다.

## 2. 검토한 대안과 기각 이유

- **완전한 인증(회원가입·로그인·세션 관리)**: 이 프로젝트가 증명하려는 것은 "슬롯 경쟁 확정의 정합성과 이벤트 신뢰 전파"이지 인증 자체의 정합성이 아니다. 인증을 넣으면 구현 시간이 거기로 새고, 정작 증명하려는 동시성·이벤트 처리 부분이 얕아진다.
- **목(mock) 인증 헤더만 흉내**: 실제 인증 로직 없이 헤더 값만 검사하는 절충안도 검토했으나, 이 경우 "검증하지 않는 값을 검증하는 척"하는 코드가 생겨 오히려 읽는 사람에게 잘못된 신뢰를 준다. 아예 없는 것이 안 만든다는 사실을 명확히 한다.

## 3. 가장 강한 반박

실무 프로젝트에 인증 없는 API가 어디 있냐는 반박이 가능하다. 아무나 임의의 `customer_id`로 Request를 만들고 임의의 `partner_id`로 확정 처리를 호출할 수 있다는 것 자체가 완성도를 의심받는 지점이 될 수 있다.

## 4. 오버엔지니어링인가

반대 방향이 오버엔지니어링이다. 이 프로젝트의 완료 조건 어디에도 인증 관련 항목이 없다. 인증을 넣으면 `Customer`/`Partner`에 없던 필드(email, password_hash, role)와 보안 요구사항(비밀번호 정책, 토큰 만료)이 새로 생겨, 이 프로젝트가 증명하려는 것과 무관하게 범위만 커진다.

## 5. 언제 이 결정을 뒤집어야 하는가

이 프로젝트를 실제 배포·공개 API로 확장해 제3자가 실제로 Request/Quote를 만들 수 있게 열어준다면(현재는 EC2에 앱만 올리고 API 응답만 확인하는 수준) 최소한 API 키 수준의 인증이 필요해진다. 또는 "인증 없이 아무나 확정 처리를 호출할 수 있는 게 이상하다"는 지적이 반복되면, 그때 인터페이스 수준(헤더의 `partner_id`를 그대로 신뢰하지 않고 검증하는 계층)만이라도 추가하는 걸 재논의한다.

## 6. 거쳐온 경로

해당 없음

## 인증을 넣었다면 설계가 어떻게 달라졌을지

`Customer`에 `email`/`password_hash` 같은 인증 필드가 필요해지고, Request 생성 API가 인증된 세션의 `customer_id`를 신뢰해 FK로 채우는 구조가 됐을 것이다. Quote 제출도 Partner 인증을 거쳐야 하고, 확정 API는 "이 Request의 소유 Customer만 확정 가능"이라는 인가(authorization) 체크가 추가됐을 것이다. 지금은 이 체크가 없으므로, API가 임의의 `customer_id`/`partner_id`를 그대로 받아 신뢰한다는 사실을 이 문서로 명시해 둔다.
