# 저장소 선택

## 1. 무엇을 결정했는가

MySQL 8 단일 저장소로 간다. Redis, MongoDB를 도입하지 않는다.

## 2. 검토한 대안과 기각 이유

- **Redis 분산 락으로 슬롯 경쟁 제어**: 불변식 1의 계층은 아직 정하지 않았고, MySQL 자체의 트랜잭션·락·유니크 제약만으로 지킬 수 있는지부터 검증하는 게 먼저다. Redis를 미리 끌어오면 "왜 MySQL만으로는 안 됐는지"를 직접 겪지 못한 채 바로 외부 저장소로 건너뛰게 된다. 또한 Redis 락과 MySQL 트랜잭션 사이에 새로운 정합성 창(락은 풀렸는데 커밋 전)이 생겨, 오히려 지키려는 불변식 검증이 어려워진다.
- **MongoDB로 이벤트 로그·Outbox 관리**: Outbox 패턴의 핵심은 "상태 변경과 이벤트 insert가 같은 트랜잭션 안에서 커밋된다"는 것이다. 이건 관계형 DB의 트랜잭션 경계 안에 있을 때 가장 단순하게 성립한다. MongoDB로 옮기면 트랜잭션+아웃박스로 지키려는 불변식 2를 멀티 도큐먼트 트랜잭션 문제로 바꾸는 것뿐이고, 이 프로젝트가 증명하려는 지점을 다른 저장소의 문제로 떠넘기는 셈이다.

## 3. 가장 강한 반박

규모가 커지면 MySQL 단일 인스턴스로는 Outbox 폴링(Relay)과 실제 서비스 쿼리가 같은 DB 자원을 두고 경쟁하게 되고, 캐시 계층 없이 조회 성능이 나빠질 수 있다는 반박이 가능하다.

## 4. 오버엔지니어링인가

반대 방향이 오버엔지니어링이다. `docs/wiki/domain/이사_매칭_도메인_분석.md`의 규모 감각 계산에서 나온 수준(시스템 전체 하루 100건 안팎의 슬롯 경쟁)에 Redis·MongoDB를 들이는 건 검증되지 않은 확장성 요구를 미리 반영하는 것이다.

## 5. 언제 이 결정을 뒤집어야 하는가

Outbox 폴링이 실제 서비스 쿼리와 자원을 다퉈서 `outbox_oldest_pending_age_seconds` 지표가 계속 나빠지는 게 관측되면, 그때 Relay 전용 읽기 복제본이나 별도 큐잉 저장소를 재논의한다. 조회 성능이 실제로 병목이 되는 게 관측되면 캐시 계층(Redis)을 그때 다시 검토한다. 지금은 그 병목을 관측한 적이 없다.
