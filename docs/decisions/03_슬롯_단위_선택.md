# 슬롯 단위 선택

## 1. 무엇을 결정했는가

슬롯을 `(파트너, 날짜, 오전/오후)` 세 요소로 단순화한다. 시작 시각·종료 시각을 정밀하게 다루지 않는다.

## 2. 검토한 대안과 기각 이유

- **시작+종료 시각 기반 정밀 스케줄링**: 실제 짐싸 앱 자체가 종료 시각을 입력받지 않는다(`docs/wiki/domain/이사_매칭_도메인_분석.md` 관찰). 앱도 정밀 스케줄링을 하지 않는다는 신호로 읽었다.
- **소요시간 추정치를 넣어 파트너별 capacity를 계산하는 방식**: 짐 규모·층수·엘리베이터 유무·이동 거리에 좌우되는 별도의 추정 로직이 필요하다. 이 프로젝트가 증명하려는 건 슬롯 경쟁의 확정·무효화 신뢰성이지 소요시간 추정 알고리즘이 아니다.

## 3. 가장 강한 반박

소형 이사가 하루 여러 건 가능한 현실을 반나절 단위로 뭉개면, 실제로는 안 겹치는 두 이사(오전 1시간짜리 + 오후 늦게 1건 더)를 시스템이 "같은 슬롯"으로 오판해 불필요하게 견적 하나를 무효화할 수 있다. 이건 파트너에게 실질적 손해(잡을 수 있었던 일을 놓침)다.

## 4. 오버엔지니어링인가

반대로, capacity·소요시간 기반 스케줄링을 지금 구현하는 게 오버엔지니어링이다. 그 정밀도가 필요하다는 근거(실제 앱의 겹침 처리 정책, 소요시간 데이터 출처)가 확인되지 않았다(도메인 분석 문서의 "확인하지 못한 것" 절 참고).

## 5. 언제 이 결정을 뒤집어야 하는가

실제 앱의 겹침 처리 정책(같은 파트너가 하루에 여러 건 확정된 실제 사례, 그 시간 간격)을 실제로 관찰해 확인하게 되면, 또는 이 모델의 한계(불필요한 무효화)가 실사용에서 문제로 확인되면, 파트너별 capacity 또는 소요시간 기반 스케줄링으로 확장한다.
