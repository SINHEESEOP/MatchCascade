# 불변식

시스템이 어떤 상태에 있든 항상 참이어야 하는 문장. 설계는 결국 아래 목록을 나열하고 각각을 어느 계층이 지킬지 정하는 일이다.

| # | 불변식 | 지키는 계층 |
|---|---|---|
| 1 | 한 파트너의 (날짜, 시간대) 슬롯에 CONFIRMED 견적은 최대 하나다 | **(탐색 중)** |
| 2 | 확정이 커밋되면 그 이벤트는 반드시 Outbox에 있다 | 트랜잭션 |
| 3 | Outbox에 있는 이벤트는 결국 발행된다 | Relay |
| 4 | 같은 이벤트가 같은 컨슈머에서 두 번 처리되지 않는다 | 컨슈머(`dedup_key` UNIQUE) |
| 5 | 컨슈머가 처리에 실패하면 그 이벤트는 유실되지 않는다 | 컨슈머(처리와 dedup 기록이 한 트랜잭션) |
| 6 | 계속 실패하는 메시지가 큐를 막지 않는다 | 브로커(DLQ) |
| 7 | 견적의 가격은 생성 시점 이후 변하지 않는다 | 도메인(스냅샷) |

## 왜 이 계층인가 (2-7)

- **2 (트랜잭션)**: Quote를 CONFIRMED로 바꾸는 것과 OutboxEvent를 insert하는 것이 같은 트랜잭션 안에 있으면, 커밋되지 않는 한 Quote 상태도 안 바뀐다. "확정은 됐는데 이벤트가 없는" 상태 자체가 만들어질 수 없다. 트랜잭션 밖에서 따로 발행하면 롤백돼도 이벤트만 나가는 유령 이벤트가 생긴다. 이 현상은 직접 재현해서 검증한다.
- **3 (Relay)**: 트랜잭션은 DB 안의 일이고 브로커로 실제로 보내는 건 DB 밖의 일이라 트랜잭션이 못 지킨다. Outbox 테이블을 폴링해서 안 보낸 것만 재시도하는 별도 프로세스가 지킨다.
- **4 (컨슈머, `dedup_key` UNIQUE)**: 같은 키로 두 번 insert하면 DB가 그 자체로 거부한다. 컨슈머 코드가 "이미 처리했나?"를 if문으로 판단하게 두면 그 판단 로직에 우회 경로(레이스, 캐시 미스)가 생긴다.
- **5 (컨슈머, 처리와 dedup이 한 트랜잭션)**: dedup 기록만 먼저 커밋하고 실제 처리가 나중에 실패하면 "처리된 걸로 기록만 되고 실제로는 처리 안 된" 상태가 생긴다. 불변식 4를 지키려다 불변식 5를 깨는 흔한 실수다.
- **6 (브로커, DLQ)**: 재시도 횟수를 컨슈머 코드가 스스로 세게 하면 그 카운터 자체가 실패하거나 리셋될 수 있다. 브로커(RabbitMQ)가 재시도 횟수를 세고 초과 시 격리하게 하면 컨슈머 코드의 상태와 무관하게 보장된다.
- **7 (도메인, 스냅샷)**: "가격이 안 변한다"는 DB 제약이나 트리거로 표현하기 애매하다(변경 자체를 막는 게 아니라 생성 시점 값을 별도로 붙잡아두는 문제라서). Quote 생성 시점에 파트너가 부른 가격을 Quote 자신의 컬럼으로 복사해서 저장하는 도메인 로직으로 지킨다.

## 불변식 1 후보 정리 (순위 없음)

아래 후보를 직접 돌려보고 결론을 낸다. 여기서는 후보 세 개와 각각 무엇을 걸고 무엇을 못 막는지만 적는다.

| 후보 | 무엇을 거는가 | 이것만으로는 못 막는 것 |
|---|---|---|
| DB UNIQUE 제약 (생성 컬럼으로 `status=CONFIRMED`일 때만 값이 채워지는 부분 유니크) | 같은 (partner, date, time_slot) 조합이 동시에 두 번 CONFIRMED로 커밋되는 것(두 번째 커밋 시도가 `Duplicate entry` 에러로 즉시 거부됨) | 경쟁에서 진 나머지 견적들을 INVALIDATED로 옮기는 후속 처리 자체(별도 애플리케이션 로직 필요), 그리고 이 락이 로우 레벨이 아니라 인덱스 레벨이라 락 대기 시간·데드락 패턴이 비관적 락과 다르게 나타날 수 있음 |
| 낙관적 락 (`@Version`) | 읽은 시점과 쓰는 시점 사이에 다른 트랜잭션이 같은 Quote 로우를 먼저 바꿔버린 경우를 커밋 시점에 감지 | 서로 다른 로우(경쟁 중인 다른 Quote들)를 대상으로 하는 확정은 각자 버전 충돌 없이 통과할 수 있음. Quote 단위 락이지 슬롯 단위 락이 아니므로, 슬롯 유일성 자체는 별도 장치 없이는 이 락만으로 보장되지 않음 |
| 비관적 락 (`SELECT ... FOR UPDATE`) | 슬롯(또는 대표 로우)에 대한 명시적 행 잠금으로 경쟁하는 트랜잭션들을 순차 대기시킴 | 잠글 대상 로우가 먼저 존재해야 함(지금 이 슬롯 자체가 별도 로우인지 미정), 대기하는 트랜잭션 수가 늘어나면 커넥션 풀 고갈로 이어질 수 있음 |
